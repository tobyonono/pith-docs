Every project at Pith starts in Figma. Whether it's a marketing site, a design system, or a complex digital product, our Figma workflow keeps design consistent, collaborative, and development-ready from day one. This page documents the standards every Pith designer follows — covering file setup, the three design phases, component library rules, review conventions, client collaboration guidelines, and the plugins we rely on.

## Project Setup Checklist

Before a single frame is sketched, the file needs to be set up correctly. A well-structured file saves hours of confusion later — for the team, for clients, and for handoff.

<Steps>
  <Step title="Create a new Figma team project">
    Name the project using the format `[Client] — [Project Type]`, for example `Acme Corp — Brand Website` or `Northlight — Design System`. This keeps the team workspace scannable and consistently labelled.
  </Step>
  <Step title="Duplicate the Pith Starter File">
    Never start from a blank canvas. Duplicate the **Pith Starter File** from the team library as your base. This brings in the correct page structure, master frames, and base styles out of the box.
  </Step>
  <Step title="Set up the page structure">
    Ensure the file has the following pages in this order: **Cover**, **Design**, **Components**, **Prototypes**, **Archive**. Use the Archive page to store deprecated frames rather than deleting work — history has a habit of being useful.
  </Step>
  <Step title="Link the shared Pith component library">
    Go to **Assets → Team Libraries** and enable the **Pith Component Library**. All shared components, icons, and patterns live here. If the library isn't appearing, check with your team lead — it may need to be published or your permissions updated.
  </Step>
  <Step title="Set up color variables and text styles">
    Import or create color variables and text styles that reflect the project's brand tokens. Variable names should follow the format `color/brand/primary`, `color/neutral/100`, etc. Never use raw hex values — everything should reference a named token from the outset.
  </Step>
  <Step title="Add project metadata to the Cover page">
    The Cover page is the file's front door. Fill in the metadata frame with: **client name**, **project name**, **start date**, and **team members** (with roles). Update the status label (e.g. In Progress, In Review, Shipped) as the project evolves.
  </Step>
</Steps>

## Design Phases

Figma work at Pith moves through three distinct phases. Each has a clear purpose and a defined home inside the file.

### Exploration

The Design page hosts rough concepts, reference moodboards, and multiple directions — typically labelled **Direction A**, **Direction B**, and **Direction C**. Fidelity is intentionally low here. The goal is to generate divergent thinking, not pixel-perfect screens. Clients and stakeholders review this phase to align on direction before deeper investment.

### Refinement

Once a direction is selected, it's developed at full fidelity. Layouts are tightened, spacing tokens are applied, and reusable patterns are extracted into the Components page. This is where the design starts to feel real — responsive considerations are introduced, and the component architecture begins to take shape.

### Spec-Ready

The final phase before handoff. Every screen covers all meaningful states (empty, loading, error, success). Annotations are added to clarify behaviour, edge cases, and responsive logic. Nothing moves to development until a design is explicitly marked spec-ready.

## Component Library Usage

Components are the backbone of a consistent, scalable design. Follow these principles without exception:

- **Always reach for the shared Pith library first.** Before creating anything new, check whether the pattern already exists in the team library.
- **Project-specific components live on the Components page** of the working file. Keep them tidy, auto-layout where possible, and properly named.
- **Never detach a shared library component unless you're intentionally extending it.** Detaching severs the link to future library updates. If you need a variant, create one via the component's properties or build an extension component that wraps the original.
- **Contribute back.** If you design a project component that would be useful across other projects, propose it for inclusion in the shared Pith library — raise it with your team lead or post a proposal in the team's design channel.

## Review Process

Design reviews at Pith are async-first. We use Figma's built-in commenting tools to keep feedback contextual and traceable.

- **Use Figma comments** to leave feedback directly on frames — no screenshots in chat, no vague emails.
- **Tag the relevant reviewer** with an `@mention` so they receive a notification. Don't assume someone will check the file unprompted.
- **Resolve all comments** before moving from one phase to the next. Unresolved comments are a signal that something is unfinished.
- **Use version history** to snapshot the file before and after major reviews. Name snapshots clearly: `Pre-Review v1`, `Post-Client Review — Direction Confirmed`. This creates a reliable audit trail.

<Note>
  Version history snapshots are free and unlimited on Figma's Organisation plan. Get into the habit of naming snapshots before every client review and after every significant round of changes — it takes ten seconds and has saved projects more than once.
</Note>

## Collaboration with Clients

Clients are stakeholders, not collaborators in the file. Protecting the working environment keeps the design process clean.

- **Share view-only links** for all client-facing reviews. View-only links let clients navigate frames and leave comments without touching the design.
- **Never give clients edit access** to working files. Even well-intentioned edits can break component structure, layer naming, and auto-layout.
- **Create a `Client Review` page** with clean, presentation-ready frames. Isolate only the work that's ready for client eyes — strip out explorations, notes to self, and work-in-progress frames before sharing.

## Plugins Pith Relies On

These plugins are installed as standard for every Pith designer. They cover the gaps Figma doesn't address natively.

<CardGroup cols={2}>
  <Card title="Figma Tokens / Variables" icon="sliders">
    Manages design tokens — colors, spacing, typography, and radius — as structured, exportable data. Keeps Figma in sync with the codebase token definitions.
  </Card>
  <Card title="A11y" icon="universal-access">
    Accessibility annotation kit and contrast checker. Use it to annotate focus order, ARIA roles, and verify color contrast ratios meet WCAG AA (or AAA where required).
  </Card>
  <Card title="Lorem Ipsum" icon="align-left">
    Fills text layers with realistic placeholder content at variable length. Far faster than typing dummy text manually, and better than leaving empty layers.
  </Card>
  <Card title="Unsplash" icon="image">
    Pulls high-quality placeholder photography directly into Figma frames. Keep images realistic to the use case — a hero image placeholder shouldn't be a random landscape.
  </Card>
  <Card title="Iconify" icon="icons">
    Access to hundreds of open-source icon sets without leaving Figma. Use it to explore icon options during exploration, then confirm the final set with the developer before locking in.
  </Card>
</CardGroup>
